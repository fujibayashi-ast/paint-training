# 開発ガイド（人間向け）

スキル名やコマンドを覚える必要はない。自然な日本語で Claude に依頼するだけで、裏で必要な手順を通してくれる。

途中で確認が必要な場面（プラン提示・PR 作成前など）では一度止まるので、内容を見て OK / NG を伝える。

---

## 最初にやること: プロジェクトのセットアップ

テンプレートから新規リポジトリを作成したら、最初に Claude にセットアップを依頼する。

> 「このプロジェクトのセットアップをお願いします」

→ Claude がプロジェクトの情報（名前・技術スタック・アーキテクチャなど）を順番に質問してくるので、答えていくだけで以下が整う:

- `CLAUDE.md` にプロジェクト固有のルール・技術スタック
- `README.md` をプロジェクト用の内容に書き換え
- 必要に応じて `docs/architecture.md` などの初期ドキュメント作成
- 配布物がある場合はビルド手順（`docs/claude/build.md`）
- CI の有効化（GitHub Actions の設定）

分からない項目があれば「後で記入」と答えればスキップできる。最後に実施サマリが提示されるので、未記入の項目を後から埋めればよい。

### 業務用プロジェクトの場合

セットアップ後、Claude による副作用（外部への push / クラウド操作 / 機密ファイル読取など）をブロックしたい場合:

> 「safe モードにしてください」

→ より厳格な権限設定に切り替わり、業務で事故が起きにくくなる。必要に応じて Dev Container による物理隔離も提案される。

## ケース別: こんなときの頼み方

### 新しい機能の要望を思いついた

> 「ログイン画面にパスワードリセット機能を追加したい。Issue にしておいて」

→ Claude が要件を整理して Issue を作成する。あとでそのまま実装を依頼できる。

---

### 既存 Issue の実装をお願いしたい

> 「#12 のタスクをお願いします」

→ Claude が [workflow.md](workflow.md) に沿って以下を進める:

1. Issue の内容と関連ドキュメントを確認
2. 実装プランを立てて Issue にコメント投稿 → ユーザーに確認
3. プラン確定後に実装
4. セルフレビュー
5. PR 作成

プラン提示・PR 作成の前に止まるので、内容を確認して進めてもらう。

---

### バグを見つけた

> 「稼働ボタンを連打すると重複で登録される。直して」

→ Claude が Issue を作ってから実装〜PR まで進める。どんな小さなバグでも Issue を経由する（履歴を残すため）。

---

### PR にレビュー指摘が来た

> 「PR #42 のレビュー対応お願い」

→ Claude がレビューコメントを読み込み、対応方針を整理して提示する。確認後、修正コミットと返信まで行う。

---

### 実装を急いでドキュメントが追いついていない

> 「最近マージした PR の内容をドキュメントに反映して」

→ 実装とドキュメントの差分を Claude が洗い出し、該当する docs を更新する。サイトマップ（`docs/README.md`）も同時に更新される。

---

### リリースしたい

> 「v1.2.0 でリリースして」
> 「パッチリリースお願い」（バージョンは Claude が判断して提案）

→ 前回リリースからの変更内容を集めてリリースノートを作成し、GitHub Release を作成する。配布物があれば自動でアップロードされる（`docs/claude/build.md` の設定による）。

---

### 作業を始めたばかりで何からやるか迷っている

> 「今ある Issue を見せて、優先度の高いものを提案して」

→ Issue 一覧と概要を出してくれる。着手するものが決まったら「#N のタスクをお願い」で進められる。

---

## 依頼するときのコツ

- **具体的に**: 「直して」より「◯◯の時に△△になるのを直して」の方が精度が上がる
- **スコープを示す**: 「この Issue の範囲だけ」「他は触らないで」と言うとスコープ外の変更を防げる
- **途中で止めてよい**: 方向性がズレたら「一旦ストップ」で止めて、方針を再指示できる
