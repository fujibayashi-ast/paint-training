# プラン作成（Issue に残す）

プランは Plan Mode（Opus）で作るのが基本。この Skill は、そのプランを Issue のコメントに残す手順を担う。Plan Mode は読み取り専用で Issue に投稿できないため、投稿は Plan Mode を抜けてから行う。

組み込みの `/plan`（Plan Mode に入るコマンド）とは別物。

## ルール

- 実装前に必ずプランを作成する
- プランは対象 Issue のコメントとして投稿する
- Issue のスコープを超えない内容にする

## 手順

### 1. Issue を確認する

Issue 番号が `$ARGUMENTS` で渡された場合はその Issue を確認する。渡されていない場合はユーザーに確認する。

```bash
gh issue view {番号}
```

### 2. Plan Mode で作成済みのプランがあるか確認する

会話内に Plan Mode で承認されたプランがあるか確認する。

- **ある場合**: その内容を使う。手順 3 の項目に沿っているか確認し、足りない項目だけ補う。プランをゼロから作り直さない
- **ない場合**: ユーザーに Plan Mode で作ることを勧める。ユーザーがこの場で作ることを望んだ場合のみ、手順 3 の項目に沿って自分で作る（手順 2.1 の調査を行う）

#### 2.1 関連ドキュメントを確認する（自分で作る場合のみ）

Issue の内容に応じて `docs/` 配下の関連ドキュメント（要件・UI 仕様・アーキテクチャ・DB スキーマなど）を確認する。

### 3. プランの項目を整える

プランには以下を含めること:

- **概要**: 何をするか（1〜3 行で簡潔に）
- **背景・目的**: なぜこの実装が必要か（Issue 本文をそのまま貼るのではなく、自分の言葉で整理する）
- **仕様**: 具体的な振る舞い・ルール・エッジケース
- **実装手順**: ステップごとの変更内容（ファイルパス・関数名レベルで具体的に）
- **スコープ外**: 今回やらないこと（スコープ超過の防止）
- **テスト・確認手順**: 実装後にユーザーが動作確認できる手順
- **影響範囲・リスク**: 既存機能への影響、データ移行、破壊的変更など（該当する場合）

### 4. プランをユーザーに提示する

Issue にコメントを投稿する前に、内容をユーザーに提示して確認を取る。Plan Mode で承認済みのプランを、項目を変えずに投稿する場合も、投稿することの確認は取る。

### 5. Issue にコメントとして投稿する

確認が取れたら対象 Issue にコメントとして投稿する。

```bash
gh issue comment {番号} --body-file -
```

（標準入力からプラン本文を渡す。HEREDOC を使うとフォーマットが崩れにくい）
