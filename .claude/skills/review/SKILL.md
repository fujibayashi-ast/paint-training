# セルフレビュー

PR 作成前に変更内容をレビューし、問題があれば指摘する。

## 手順

### 1. Issue を確認する

Issue 番号が `$ARGUMENTS` で渡された場合はその Issue を確認する。渡されていない場合はユーザーに確認する。

```bash
gh issue view {番号}
```

Issue の目的・実装内容・非対象・完了条件を把握する。

### 2. 変更内容を把握する

```bash
git log main..HEAD --oneline
git diff main...HEAD
```

### 3. 以下の観点でレビューする

#### スコープ

- [ ] Issue の実装内容に含まれる変更のみか
- [ ] Issue の非対象に該当する変更が混入していないか
- [ ] 不要なリファクタリング・コード整理が含まれていないか

#### 品質

- [ ] 既存の設計・パターンを壊していないか
- [ ] セキュリティ上の問題がないか（XSS、インジェクション等）
- [ ] パフォーマンスに悪影響を与える変更がないか
- [ ] 不要なライブラリが追加されていないか

#### ドキュメント

- [ ] 実装に対応するドキュメント（`docs/` 配下）が更新されているか
- [ ] DB スキーマ・アーキテクチャ・UI 仕様など、変更があった領域の docs が実装と一致しているか
- [ ] プロジェクト固有のドキュメントルール（CLAUDE.md の Documentation Rules 参照）に従っているか

#### プランとの整合性

- [ ] Issue コメントに投稿されたプランと実装が一致しているか
- [ ] 乖離がある場合、Issue コメントでプランが更新されているか

### 4. 結果を報告する

以下の形式で報告する:

- **OK**: 問題なし。`/pr` で PR を作成して良い
- **要修正**: 問題点を具体的に列挙する。修正後に再度 `/review` を実行する
