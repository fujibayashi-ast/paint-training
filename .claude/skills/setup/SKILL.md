# プロジェクト初期セットアップ

## ルール

- ヒアリング項目は `docs/claude/setup.md` に定義されている
- 回答は 1 セクションずつ確認しながら進める
- 該当しない項目は無理に埋めず、CLAUDE.md の該当セクションごと削除してよい

## 手順

### 1. ヒアリング項目を読み込む

`docs/claude/setup.md` を Read して、ヒアリングすべき項目を把握する。

### 2. 順番にヒアリングする

`docs/claude/setup.md` の各セクションについて、ユーザーに 1 つずつ質問する。

- 質問はまとめて出さず、1 セクションずつ確認してから次に進む
- 回答が曖昧な場合は具体例を挙げて掘り下げる
- 「後で記入」でスキップされた項目は CLAUDE.md 上でコメント `<!-- 未記入 -->` として残す

### 3. CLAUDE.md を更新する

ヒアリング結果をもとに CLAUDE.md を書き換える。

- 該当しないセクションは削除する（例: Domain Rules が不要なプロジェクト）
- プレースホルダコメント（`<!-- ... -->`）は回答内容に置き換える

### 4. README.md をプロジェクト用に書き換える

テンプレート状態の README はこのテンプレート自体の説明になっているため、プロジェクト用の内容に置き換える。

- 冒頭のタイトルと概要をプロジェクトのものに変更する
- 「含まれているもの」「カスタマイズ」などテンプレート紹介セクションは、プロジェクトに応じて削除 or 書き換える
- Getting Started はプロジェクトのセットアップ手順（インストール・起動コマンドなど）に置き換える
- 情報が不足する場合はユーザーに追加ヒアリングする

### 5. 初期ドキュメントを作成する（必要に応じて）

回答内容に応じて `docs/` 配下のドキュメントを初期化する。

- アーキテクチャの説明が必要なら `docs/architecture.md`
- 要件の記載が必要なら `docs/requirements.md`
- ER 図が必要なら `docs/er.md`
- 無理に全て作らず、ユーザーが必要だと答えたものだけ作成する

### 6. ビルド・配布手順の設定（スキップ可）

`/release` スキルで配布物をアップロードする際に参照される。配布物があるプロジェクトのみ対象。

ユーザーに以下を確認する:

- このプロジェクトに配布物（実行ファイル・パッケージなど）はあるか
- ある場合、ビルドコマンドは何か（例: `make dmg` / `yarn build` / `cargo build --release`）
- アップロードする成果物のパスは何か

回答に応じて以下の分岐:

- **配布物あり**: `docs/claude/build.md` を作成し、ビルドコマンド・成果物パス・注意点を記載する
- **配布物なし / 後で設定**: スキップする（`/release` のステップ 5 は自動的にスキップされる）

後から設定したい場合、ユーザーに「`docs/claude/build.md` を作成して、ビルドコマンドと成果物パスを記載してください。`/release` がそれを参照します」と案内する。

### 7. CI の設定（スキップ可）

`.github/workflows/ci.yml` が雛形として含まれている。

ユーザーに以下を確認する:

- このプロジェクトで CI を有効にするか
- 有効にする場合、実行したいチェック（例: lint / typecheck / test / build）

**Yes の場合**:

1. ヒアリング済みの技術スタックに応じて `.github/workflows/ci.yml` を埋める
   - Node (yarn/npm/pnpm) なら `actions/setup-node` + 該当の install / lint / typecheck / test コマンド
   - Python (pip / uv / poetry) なら `actions/setup-python` + 該当の install / lint / test コマンド
   - Go / Rust / Ruby など他言語も同様
2. プロジェクトで使うコマンド名（`yarn test` など）が不明な場合はユーザーに確認する

**No の場合**:

1. `.github/workflows/ci.yml` を削除する
2. `.github/workflows/` 配下に他のファイルがなければディレクトリごと削除する

後から CI を追加したい場合は、GitHub Actions の公式ドキュメントまたは他プロジェクトを参考に新規作成するよう案内する。

### 8. 使う skill を選定する

テンプレートには汎用的な skill が一通り含まれている。このプロジェクトで使わない skill は `.claude/skills/` から削除し、リポジトリと Claude のコンテキストをクリーンに保つ。

1. `.claude/skills/` を列挙し、各 skill の `name` / `description` を提示する。
2. ユーザーに、このプロジェクトで使う skill を選んでもらう（残すもの／消すもの）。
   - `skill` 管理スキル自体は、後から skill を追加・更新するために **原則残す**ことを勧める
   - `setup`（このスキル）は初期化専用のため、不要なら削除候補に含めてよい
3. 使わないと選ばれた skill を `rm -rf .claude/skills/<name>` で削除する。

後から skill が必要になったら `/skill add <name>` でテンプレートから取得できる旨を案内する。詳細は `docs/claude/skills.md` を参照。

### 9. 結果を報告する

各ステップの実施状況をチェックリスト形式で提示する。チェック済み・スキップ・未実施をそれぞれ明示し、スキップや未実施の項目には理由を添える。

フォーマット例:

```
## セットアップ実施サマリ

- [x] CLAUDE.md 更新
- [x] README.md をプロジェクト用に書き換え
- [ ] 初期ドキュメント作成: スキップ（ユーザーの指示で未作成）
- [x] ビルド・配布手順: docs/claude/build.md を作成
- [x] CI: .github/workflows/ci.yml を Node 用に構成
- [ ] safe モード: 未適用（業務用なら /safe-mode で適用可能）

## 未記入のまま残した項目

- CLAUDE.md の Domain Rules セクション（後で記入）
```

業務用プロジェクトなどで副作用ブロックの厳格モード（safe モード）を適用したい場合は、続けて `/safe-mode` スキルを実行するようユーザーに案内する。

ステップ 1〜7 の各処理中に「実施した／スキップした／理由」を覚えておき、ここでまとめて出力すること。
